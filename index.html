06

The delivery run uses every system component

The final response depends on the work performed across the complete system.

Goal

Resolve the delivery problem rather than answer a tracking question.

Model

Understands the intent and selects the delivery investigation capability.

Context

Provides the conversation, order history, and applicable delivery policy.

Tools

Access order, shipment, carrier, incident, and eligibility systems.

State

Records the order, six-day delay, incident check, and collected evidence.

Execution loop

Reviews each result and decides whether more evidence is needed.

Controls

Block unsupported refunds and require approval for consequential actions.

The valuable work happens before the final sentence: evidence retrieval, policy application, state management, and authority checks.

This is manageable with five distinct capabilities. What changes when the agent can see fifty overlapping tools?

A system can investigate independently while keeping consequential actions under human control.

3

Autonomy has several controls: tool selection, sequencing, execution authority, stopping conditions, and approval requirements.

04

Five stages shaped modern agentic systems

Each stage increased what the system could access, decide, or execute.

  1. Before 2022Generate and retrieve

    Models produced text and used retrieved documents for grounded answers.

  2. 2022Reason and act

    ReAct showed how models could interleave reasoning with actions.

  3. 2023Call functions

    Structured function calling connected models to application logic.

  4. 2024Connect systems

    MCP standardized connections to tools and enterprise data.

  5. 2025–26Govern execution

    Tracing, approvals, evaluation, and sandboxing became production concerns.

Sources: ReAct paper, OpenAI function calling announcement, Anthropic MCP announcement, and OpenAI agent documentation

07

Direct tool exposure creates production costs

The impact extends beyond choosing the wrong tool.

01

Routing ambiguity

Similar tools make selection and argument choice less reliable.

02

Latency and failures

Sequential calls add waiting, retries, timeouts, and dependency failures.

03

Token and context cost

Tool schemas and raw results consume context that the model needs for evidence.

04

Inconsistent execution

The same request can follow a different sequence and produce a different outcome.

05

Evaluation and debugging

More possible paths make failures harder to reproduce, trace, and isolate.

06

Security and authority

The model may see sensitive data or action tools outside its responsibility.

Tool count alone does not create the problem. Risk grows when tools overlap, workflows repeat, and low-level implementation reaches the main model.

Approach 1: the prompt owns the workflow

The model receives every low-level tool and the instructions for applying the decision logic.

You assist loan officers with product eligibility.

For the selected applicant and loan product:

1. Call get_identity_status(applicant_id)
2. Call get_verified_income(applicant_id)
3. Call get_debt_obligations(applicant_id)
4. Retrieve the current product thresholds
5. Calculate the debt-to-income ratio
6. Apply every eligibility requirement

If any required data is missing, do not decide.

Return:
- eligible: true or false
- failed requirement
- reason for the loan officer
The model must
  1. Select four tools
  2. Sequence the calls
  3. Interpret each response
  4. Perform the calculation
  5. Apply the product rules
  6. Handle missing data
  7. Explain the decision

One prompt now owns routing, sequencing, arithmetic, policy application, error handling, and explanation.

18

Implementation lessons from both cases

The delivery investigation and eligibility decision use the same design discipline.

  1. 01Start with a recurring business question

    Define the outcome the user needs and the stopping condition.

  2. 02Create one bounded domain capability

    Give it a clear purpose, inputs, output, authority, and failure behavior.

  3. 03Put predictable choreography in software

    Code should own standard retrieval, calculations, joins, and policy checks.

  4. 04Return structured evidence

    Include the result, reason code, evaluated factors, missing inputs, and evidence references.

  5. 05Separate investigation from action

    Reading evidence and recommending an option should not automatically authorize a consequential action.

  6. 06Evaluate each layer independently

    Test routing, retrieval, rules, evidence assembly, explanation, and authorization.

Give the model the smallest meaningful problem that still requires judgment.

Design question 2

Where should reasoning happen?

Based on “Designing Reasoning Boundaries in Agentic Systems”

11

The three execution layers

Each layer owns a different kind of decision and exposes a clear contract to the next one.

Ordinary software

Compute and enforce

  • Retrieve records from known systems
  • Calculate exact values
  • Apply policy and permission rules
  • Validate schemas and allowed values
Bounded inner model

Interpret evidence

  • Classify unstructured notes
  • Extract findings from messy text
  • Return typed fields with evidence references
  • Stay inside a narrow semantic task
Main model

Understand and explain

  • Interpret the user’s goal
  • Ask for missing information
  • Synthesize the supported result
  • Explain the available options
Human approval boundaryConsequential actions cross an explicit authority check before execution.

Use software when the answer can be computed. Use a model when the input must be interpreted.

12

Two bad reasoning boundaries

Both failure modes assign work to a mechanism that cannot guarantee the right behavior.

Failure mode 1

The model becomes the calculator

“Read these timestamps, calculate the delay, apply the refund threshold, and verify the approval limit.”

  • Exact work depends on prompt interpretation
  • Small wording changes can alter the result
  • Policy enforcement becomes difficult to test
Failure mode 2

Code becomes the language interpreter

if "lost" or "stuck" or "not moving" ...

  • Rules multiply as language varies
  • Ambiguous evidence falls through brittle branches
  • Maintenance grows faster than coverage

Boundary rule: Put computable work in software. Use a bounded model call for semantic interpretation.

13

A practical reasoning-boundary test

Start with the nature of the work, then assign the narrowest mechanism that can perform it reliably.

Nature of the workMechanismExample
Retrieve a known recordAPI or databaseOrder and shipment lookup
Transform or calculate an exact resultCodeDays delayed
Apply a fixed policy conditionRulesReplacement eligibility
Interpret unstructured evidenceBounded LLMMeaning of a carrier note
Synthesize an open-ended responseMain LLMExplain supported options
Approve a high-impact exceptionHumanAction beyond agent authority

Treat every model output as untrusted input. Validate its schema, allowed values, evidence references, and required fields.

Design question 3

How do we know it worked?

Based on “How Do You Evaluate an Agent That Calls Tools That Call Other Tools?”

15

Evaluation measures how reliably the agent behaves

Agent quality includes the decisions and evidence behind the final answer.

Evaluation is a repeatable process for measuring whether an agent makes the right decisions, uses the correct evidence, follows policy, and completes the user’s task across representative cases.
Behavior varies

Similar requests can produce different tool choices and execution paths.

Failures stay hidden

A polished answer can conceal an incorrect record, rule result, or unsupported claim.

Changes create regressions

A model, prompt, tool, policy, or adapter change can shift behavior elsewhere.

Actions have consequences

Incorrect refunds, approvals, or account actions can create real operational harm.

Evaluation measures both the outcome and the path the system used to reach it.

Match the evaluator to the decision

The cheapest reliable evaluator depends on whether the answer is exact, semantic, or consequential.

Code

Known answers

  • Tool name and arguments
  • Shipment and evidence IDs
  • Calculations and policy outcomes
  • Schema and allowed values

Run on every relevant case.

Bounded LLM judge

Semantic questions

  • Summary preserves source meaning
  • Explanation contains no distortion
  • Important qualifications remain

Use a narrow rubric and validate the judge.

Human review

Costly or uncertain cases

  • Disputed refunds
  • Policy exceptions
  • Irreversible actions
  • Evaluator disagreement

Focus review where mistakes have the highest cost.

Model judges add cost and uncertainty. Keep exact checks in code.

The same bad answer can have different causes

Layer scores tell the team where to investigate instead of treating every failure as a prompt problem.

Routing failure

Wrong capability

The model selected generic search instead of the delivery investigation.

Investigate

Evidence failure

Investigate

23

Offline evaluation and production monitoring

The two environments answer different questions and use different evidence.

Before deployment

Is the system correct on labeled cases?

  • Expected tool, evidence, rules, and allowed claims
  • Release gates for every layer and the complete task
  • Run after model, prompt, tool, policy, or adapter changes
  • Segment by intent, carrier, language, and edge case
In production

Where may the live system be degrading?

  • Dependency and schema failures
  • Missing, stale, or incomplete evidence
  • Policy invariant violations
  • Latency, cost, fallback, and escalation
  • Sampled human or model review for correctness

Production traces rarely contain ground truth. Report the reviewed sample size beside any estimated quality score.

Evaluation operating model

Evaluation becomes useful when it runs before release and learns from production failures.

  1. 1Build the dataset

    Label common paths and the edge cases that matter.

  2. 2Define expected behavior

    Specify the tool, evidence, rules, and allowed claims.

  3. 3Automate exact checks

    Use code for deterministic facts and invariants.

  4. 4Judge semantic work

    Use narrow rubrics for summaries and explanations.

  5. 5Capture the trace

    Preserve inputs, decisions, evidence, and outcomes.

  6. 6Gate the release

    Set thresholds for each layer and the full task.

  7. 7Monitor production

    Track health signals and review a labeled sample.

  8. 8Learn from failures

    Add discovered cases back into the evaluation set.

The final-answer score shows whether the user received a useful result. The layer scores explain why that result changed.

Reliable agents have deliberate boundaries

Control the decisions

Give the model domain capabilities and reserve model reasoning for tasks that require interpretation.

Preserve the evidence

Trace and evaluate every layer before trusting the final answer or action.

The goal is the right autonomy, at the right layer, with enough evidence to trust the outcome.
